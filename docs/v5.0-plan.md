# Jacob's Cookbook — v5.0 Plan

Scoped October 5, 2026. Starting point is v1.2.0 (April 7), which is what's live, on GitHub, and on disk. All three are identical. "v5.0" reflects the overall iteration count, not a jump in code.

Desktop first. Mobile polish waits until desktop is right.

---

## What's in v5.0

0. Housekeeping: fix CLAUDE.md, rotate the GitHub token, clean working tree
1. AI upgrades: model, output limit, proxy lockdown, prompt caching + cache diagnostics
2. New recipe fields + structured outputs: reheat instructions, early prep, dish role
3. Meals vs dishes: meals link one main + one or two sides; existing combo recipes get split
4. Import: recipe-site URLs (primary), PDFs (stretch)
5. Twist: "Give me a twist" button on recipe pages

Out of scope: mobile polish, on-demand compaction (beta, extra API call, chats aren't long enough to need it), visual output generation.

---

## Build order

Each phase goes on `dev`, then through `/health` → `/review` → `/ship`, then deploys. Phases ship one at a time so nothing big lands at once. The order matters: phase 2 defines the recipe schema that phases 3–5 all write to.

### Phase 0 — Housekeeping

No feature work until these are done.

- Fix `.claude/CLAUDE.md`. It describes the abandoned Next.js + Supabase version, so every Claude Code session starts with the wrong picture. Rewrite it for the real stack: single `index.html`, Firebase Hosting + Firestore + Auth, Cloud Function proxy.
- Rotate the GitHub token. The current one sits in plain text in the git remote URL. Generate a new token, revoke the old one, set the remote to the plain `https://github.com/jacobgreenwald21/jacobs-cookbook.git`, and let the macOS Keychain store the new token on the next push.
- Clean up uncommitted files on `dev` (CLAUDE.md edits, handoff v6, site-template-context). Commit or clear them so phase 1 starts clean.
- Possibly update the make-pdf skill so plan docs like this one can be exported to PDF. Optional; doesn't block phase 1.

Done when: `git remote -v` shows no token, a push works through Keychain, `git status` is clean, and CLAUDE.md matches the real app.

### Phase 1 — AI upgrades

Smallest change, immediate payoff.

- Swap `claude-sonnet-4-20250514` for the current Sonnet (`claude-sonnet-5-5`; confirm ID and pricing in the docs at build time).
- Raise `max_tokens` from 1000. Full recipes plus chat can get cut off at 1000.
- Prompt caching: the system prompt is rebuilt from the whole recipe catalog every message. Restructure it as two system blocks: static instructions first, then the catalog, with a cache breakpoint at the end. The catalog currently sits *before* the instructions, so this is a reorder too.
- Cache diagnostics: log cache read/write token counts from each response so it's visible whether caching is actually hitting. Check current docs for the GA diagnostics shape.
- Move `model` and `max_tokens` into the Cloud Function instead of letting the browser send them. Right now any signed-in Google account can call the proxy with any model and any token limit. Small fix, and the model swap touches the same lines anyway.

Done when: AI Kitchen works on the new model, and second-message responses show cache reads.

### Phase 2 — Schema + structured outputs

- Add optional fields to recipes:
  - `reheat` — short text on how to reheat leftovers
  - `early_prep` — list of things that can be done ahead (marinate overnight, chop the day before)
  - `role` — `main` | `side` | `standalone` (used by phase 3)
- Show the new fields on the detail page, the edit form, and the AI draft review form. Empty fields render nothing.
- Switch draft generation from "please return JSON" in the prompt to structured outputs with a JSON schema. With more fields, parse failures get more likely; structured outputs make the response always valid.
- Update the AI prompt so drafts fill in reheat and early prep when they make sense.

Done when: a new AI draft includes the new fields, the response never fails to parse, and existing recipes still display fine without them.

### Phase 3 — Meals vs dishes

The model: a **dish** is a single recipe (what every recipe is today). A **meal** is one main dish plus one or two side dishes, linked by ID, not copied.

- New Firestore collection `meals/{mealId}`: title, description, `main_id`, `side_ids` (1 or 2), tags. Same security rules pattern as `recipes`.
- Browse view gets a Meals / Dishes toggle. Dishes can also be filtered by role (main / side).
- Meal detail page shows the three dishes with links to each. Total time is calculated from the parts.
- Meal builder for editors: pick a main, pick one or two sides.
- If a dish is used in a meal, deleting it warns and lists the meals it breaks.
- Naming collision: the existing `meal_type` field (breakfast / dinner / snack…) now sounds like it's about meals. Relabel it "Occasion" in the UI. Field name can stay.

**Splitting existing combo recipes.** This edits live data, so it runs with a human approving each step:

1. Back up the full `recipes` collection before anything changes.
2. Pull the live recipe list and flag combos. From the April snapshot in `index.html`, likely candidates:
   - Baked Chicken Parmesan with Spaghetti
   - Honey Glazed Carrots with Lemon Garlic Chicken
   - Honey Lemon Soy Chicken (with roasted broccoli)
   - Salmon and Sweet Potato
   - Creamy Mushroom Tomato Orzo with Crispy Skin Salmon
   - Turkey Meatball Bowl (meatballs, sweet potatoes, green beans, sauce)
   - Savory Mushroom Orzo with Wine & Herb Chicken
   - Probably stays whole: Lemon-Dijon Chicken Sausage Skillet (one-pan)
3. For each combo, show the proposed split (which ingredients and steps go to which dish) and get approval.
4. Write the new dishes, create a meal linking them, and archive the original (status change, not delete).

One-side combos (e.g. Salmon and Sweet Potato) become one-side meals.

Fallback if supporting both 1 and 2 sides turns out to be messy: meals are one main + one side only.

Done when: you can browse meals and dishes separately, open a meal and click into its parts, and every approved combo is split.

### Phase 4 — Import

**Recipe-site URLs (primary).**

- New Cloud Function `importRecipe({ url })`. Signed-in editors only.
- Function fetches the page and reads its schema.org `Recipe` data, which most recipe sites embed. That maps straight onto our fields without spending AI tokens.
- Fallback when a site has no structured data: send the page text to Claude with the phase 2 schema.
- Output is always an editable draft. Never auto-publish.
- Paywalled sites (NYT Cooking) will likely block the fetch. Error message should say to paste the recipe text into AI Kitchen instead.
- Basic guardrails: http/https only, no internal addresses, size and time limits on the fetch.

**PDFs (stretch).** File picker → send the PDF to Claude through the proxy → same schema → editable draft. Cheap once URL import exists; skip if phase 4 runs long.

Done when: pasting an AllRecipes-style URL produces a correct draft, and a site without structured data still produces a usable one.

### Phase 5 — Twist

- "Give me a twist" button on each recipe detail page (signed-in editors).
- Opens AI Kitchen with that recipe loaded. Claude proposes exactly 2 distinct variations (swap a flavor profile, change the technique, adjust for a different occasion), both in a single API call. Capped at 2 to keep API usage down.
- Picking one produces a draft of a new recipe tagged as a twist of the original. The original is never changed.
- The existing similar-recipe nudge stays as is. Optionally it can point to the twist button when it flags a close match.

Done when: clicking the button on any recipe gets variations, and picking one leads to a reviewable draft.

## Rules that carry through every phase

- AI produces drafts. A human publishes. No exceptions, including import and the combo split.
- Never overwrite a published recipe automatically.
- One feature per commit. Don't touch unrelated code.
- Never open `index.html` in TextEdit.
